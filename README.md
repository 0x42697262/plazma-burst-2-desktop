# Plazma Burst 2 Desktop

An Electron wrapper for the [Plazma Burst 2](https://www.plazmaburst2.com/h5/) HTML5 game. It
plays a local copy of the game under its real URL (login, multiplayer and maps work like on
the website) and adds a developer console (Shift+`` ` ``, i.e. `~`).

The game files are **not** in this repository. You download them with a script.

## 1. Quick start

Requirements: Node.js 22.18 or newer, npm.

```bash
npm install          # Electron (its binary downloads on the first start)
npm run fetch-game   # the game files, about 57 MB, about 1 minute
npm start            # builds the page scripts (dist/page/), then starts the game
```

Working on the code: `npm run verify` runs lint, the type check, the tests and the build; see [AGENTS.md](AGENTS.md).

In the game, press Shift+`` ` `` (`~`) for the dev console and type `help`.

To run a server of your own for friends, without the official site: `npm run server`, and
they pick it in the server list `npm start` opens ([docs/operations/private-server.md](docs/operations/private-server.md)).

The community client Sad Burst 2 has commands of its own; the ones above never touch it
([section 9](#9-sad-burst-2-community-client)).

## 3. Getting the game files

### Automatic (recommended)

```bash
npm run fetch-game                  # newest version
npm run fetch-game -- v1769098419   # a specific version
```

The script:

1. Reads the current version from `https://www.plazmaburst2.com/h5/` (the "Launch" link points to `versions/v<number>/`).
2. Downloads `index.html` and everything it references (`_strings.js`, `loading_screen.css`, `scripts/...`).
3. Finds every folder mentioned in the code (`scripts/`, `flash_export/`, `fonts/`, `audio_overrides/`, `bitmap_overrides/`, `loading_screen/`) and downloads them completely through the server's directory listings.
4. Checks that every file in the sprite/sound list (`flash_export/just_sounds_and_bitmaps.html`) was downloaded.
5. Writes `game/pb2-version.json` (the app reads the version from it).
6. Moves the old `game/` to `game.previous/`, then puts the new copy in `game/`.
7. Runs `npm run find-names` (section 5).
8. Runs `npm run fetch-opcodes`: the map editor's trigger action names (`MovableTo`, ...), object parameters and value lists, which the console's `triggers exec` and in-game editor read.

The download goes into `game.download/` first, so a failed download never breaks your working copy.

> Changes you made inside `game/` are not carried over. They stay in `game.previous/` until the next update.

### Manual

Use this if the script stops working.

1. Open `https://www.plazmaburst2.com/h5/` and find the version in the "Launch" link, e.g. `v1769098419`. Below, `BASE` is `https://www.plazmaburst2.com/h5/versions/v1769098419`.
2. Download these into `game/`, keeping the folder structure:
   - `BASE/index.html`
   - every `src="..."`/`href="..."` in `index.html` that is a relative path (not `/cdn-cgi/...`)
   - every `url(...)` in `loading_screen.css`
3. Download these folders completely. Each one has a directory listing ("Index of ..."); the root folder does not:
   - `scripts/` (with `libs/` and `screens/`)
   - `flash_export/` (with `images/`, `sky/`, `sounds/`)
   - `fonts/`, `audio_overrides/`, `bitmap_overrides/`, `loading_screen/`

   With `wget`, one folder at a time:

   ```bash
   cd game
   wget -r -np -nH --cut-dirs=3 -R "index.html*" "$BASE/flash_export/"
   ```

4. Look for new folders: search the code for strings like `'name/...'` and open `BASE/name/` in a browser.
5. Create `game/pb2-version.json`:

   ```json
   { "version": "v1769098419" }
   ```

6. Run `npm run find-names`.

Missing files answer with a redirect (HTTP 302), not with 404.

## 4. Updating to a new game version

The game updates around the 20th of each month.

1. `npm run fetch-game`
2. Check the last lines of the output:
   - `Found 95 of 95 names` means the dev console works with the new version.
   - Any `problem:` line means a name was not found. See [section 5](#5-finding-the-obfuscated-names).
3. `npm start`. The terminal shows `Game v<number> from .../game`.
4. In the game, open the dev console and run a few commands (`guns`, `pos`, `give 1`).

To go back to the old version: delete `game/`, rename `game.previous/` to `game/`, run `npm run find-names`.

## 5. Finding the obfuscated names

### Why

The game's code uses random names like `$0Ме1А` for its variables (the letters are a mix of Latin and look-alike Cyrillic). They can change with every version. The dev console needs about a hundred of them: the characters array, the guns array, the heal function, and so on.

They are not written in the console's code. It reads them from `data/names.js`, and only its `game/` folder uses them:

```js
globalThis.PB2_NAMES = {
  version: "v1769098419",
  chars: '$0\u041c\u04351\u0410', // $0Ме1А  characters array (scripts/frame2.js)
  ...
};
```

### Automatic

```bash
npm run find-names                    # reads game/, writes data/names.js
npm run find-names -- --check      # only report
npm run find-names -- game.previous --out /tmp/old-names.js   # another copy
```

How it works, assuming the code structure stays the same:

1. String constants are replaced by their values. The game keeps all strings in `_strings.js` as variables (`$x = "god"`); after replacement, the code reads `$y=="god"`.
2. Each name is found with a pattern that matches the code around it. All other obfuscated names in the pattern are wildcards. For example, the characters array and your character index come from the `god` cheat command:

   ```js
   if(chatText=="god 1"||chatText=="god")
   {
   $0Ме1А[$НAlНc].hmax*=100000;     // pattern: =="god"\)\s*\{\s*⟨ID⟩\[⟨ID⟩\]\.hmax\*=100000;
   ```

3. A name must give the same result at every place the pattern matches, or it is reported as ambiguous.
4. A few extra checks confirm related names belong together (e.g. each body part's HP with its "broken" flag).

The patterns are the `RULES` list in `src/tools/find-names/constants.ts` (notes: `docs/operations/find-names.md`). They were tested by renaming all 7579 obfuscated names in the game at random: all of them were still found correctly.

### When a name is not found

The output says which one, e.g. `problem: gunRecoil: pattern not found in scripts/frame2.js`.

1. **Find the old name.** Open the old `data/names.js` (from git history, or run `npm run find-names -- game.previous --out /tmp/old-names.js`). The comment says what it is and which file it is in.
2. **Look at the old code.** Make both copies readable:

   ```bash
   npm run -s find-names -- game.previous --decode scripts/frame2.js > /tmp/old.js
   npm run -s find-names -- game --decode scripts/frame2.js > /tmp/new.js
   ```

   Search `/tmp/old.js` for the old name, and find the lines the pattern in `RULES` describes.
3. **Find the same code in the new version.** Search `/tmp/new.js` for the parts that are not obfuscated: strings (`"god"`, `"failed"`), numbers (`100000`, `0.3`), readable names (`hmax`, `picken_by`, `event.keyCode===87`, `params`).
4. **Fix the pattern** in `RULES`. Placeholders:
   - `⟨ID⟩` captures a name (in the order of `keys`)
   - `⟨_⟩` is any name, not captured
   - `⟨chars⟩` is a name found by another rule
5. Run `npm run find-names` again until it finds every name (`Found N of N`).
6. **Test in the game** with the dev console, e.g. `js eval(PB2_NAMES.chars).length` (number of characters) or `js typeof eval(PB2_NAMES.healChar)` (`function`).

Quick fix without changing a pattern: write the name into `data/names.js` by hand. The next `npm run find-names` overwrites it.

If names are missing, the dev console still opens and lists them in red. Only commands that need them fail.

## 6. Configuration

| Variable | Default | What |
|---|---|---|
| `PB2_DEV=0` | on | Turn the dev console off. |
| `PB2_HOOKS=0` | on | Turn the hooks in `hooks/` off (see `docs/features/hooks.md`). |
| `npm run host -- [options]` | off | Remote play host instead of a game window (`--port`, `--max`, `--fps`, ...; see `docs/operations/remote-play.md`). |
| `PB2_GAME_DIR` | `game/` | Play a different game copy |
| `PB2_VERSION` | from `pb2-version.json` | Version folder used in the URL |
| `PB2_LOGIN`, `PB2_PASSWORD`, `PB2_UID` | `data/credentials.json` | Login cookies |
| `--verbose` / `-v`, `--log-level=<level>`, `PB2_LOG_LEVEL` | `info` | Terminal log level: `error`, `warn`, `info` or `debug`. `--verbose` is `debug`: every request (served locally, by the dev routes or passed to the network, with status and time), window events, the page's `console.debug` and the game's own `trace()` output (silent otherwise). `npm start -- --verbose` or `npm run start:verbose` |

With the credentials above, every official start clears the game site's cookies, then sets only that account's. Without them, the game's own login is kept, and a private server never sees it: it is put aside while you play there and comes back on the official server. Saved games and settings (localStorage) are kept.

## 7. Network log

The dev console records the game's network traffic while it runs: on by default, in every game window. Each run of the app writes one plain-text file per game instance:

```
data/netlogs/<date>_<time>_local.log          this window
data/netlogs/<date>_<time>_tester-<name>.log  a remote play tester's game (src/features/remote_play/)
```

A second copy of the app started in the same second gets `..._local-2.log`. Page reloads append to the same file, after a `PAGE` line.

**A line:** time, connection, direction (`OUT` sent, `IN` received, `---` neither), kind, details. The header of each file explains every column.

```
05:30:14.200  c1 server     OUT  PKT    41 chars | ack #3 | #5 CHAT 36 chars | framing 5 chars
05:30:14.200  c1 server     OUT  REL    #5 CHAT("hello there", 12)
05:30:14.300  c1 server     OUT  REL    #6 GET_MATCH_LIST("h")
05:30:14.460  c1 server     IN   REL    #4 RESPONSE(100, "ok", [{"uid":1,"map_id":"a-b"}])  <- answers #6 GET_MATCH_LIST (its part 1, "h", was callback ID 100), 160 ms later
05:30:16.300  c1 server     OUT  LOSS   slow ack: #5 CHAT acknowledged after 900 ms, ping 45 ms (sent 50 times): packets or acks were lost on the way
05:30:16.500  c1 server     IN   LOSS   gap: #11 arrived before #9-#10 (2 missing: lost or out of order)
05:30:17.000  c1 server     ---  STAT   ping 45 ms | acks in 61 ms | out 60 packets 3174 chars (2 reliable, 58 state) | in 61 packets 12.4K chars (3 reliable, 58 state) | repeated 5 out, 4 in | loss: 1 slow ack, 1 gap
```

| Kind | What |
|---|---|
| `REL` | A reliable message, written like a call: `#<sequence number> TYPE(part, part, ...)`. Text is in quotes, numbers are bare (the game sends them encoded; they are decoded), JSON is shown as it is. The type is the game's `RELIABLE_<TYPE>` name without `RELIABLE_`. `#<n>` is always a sequence number. A `RESPONSE` ends with `<- answers #<n> <TYPE>`: the request it answers, which of its parts was the callback ID (often one letter, like `"h"` for 100), and how long the answer took |
| `LOSS` | `slow ack` (acknowledged over 500 ms after the ping), `no ack` (none after 2 s), `dropped` (socket.io dropped it, the socket was busy), `gap` (a later message arrived first), `late` (a missing one arrived) |
| `STAT` | Once a second per busy connection: ping, how long acks took, packets, characters, repeats, losses (`loss: none` when there were none) |
| `CONN` | Connected, disconnected (with the game's reason and the connection's totals) |
| `STATE` | Every unreliable state update, decoded by position. Your state: `hp 150 \| respawns 1 \| aim +212,-40 \| pos 1264,-520 \| ...`; the server's snapshot: `#3 hp 80 ping 45 ms [that player's state]` for each player. Off by default (60 to 250 a second); only counted in `STAT`. On with `net_log_state` or `net_log_all`. How HP travels: [docs/research/anticheat.md §14.9](docs/research/anticheat.md#149-how-hp-travels) |
| `PKT` | Every packet, also ack-only ones (`ack #0 \| nothing else`): its size in characters, its ack, what it carries with each item's size (`state (3 parts) 120 chars, #5 CHAT 36 chars`), and the framing: the ack, sequence numbers and separators. The sizes add up to the packet's. The `REL` and `STATE` lines after it show the contents. Only with `net_log_all` |

**Repeats are not loss.** The game repeats every message that is not acknowledged yet in every packet it sends (about every 16 ms), until the ack arrives, about one ping later. So each reliable message goes out several times, and arrives several times, on a perfect connection. `STAT` counts them (`repeated 41 out, 26 in`); only a slow or missing ack is loss.

**Why a connection closed:** the `CONN closed:` line gives socket.io's reason and what it means. `io server disconnect` is the server closing it on purpose; `transport close` and `ping timeout` are the network. What the server checks in your state updates (server-side checks: they run on the match's server, not in your game), and which of those checks disconnect you: [docs/research/anticheat.md §14](docs/research/anticheat.md#14-server-side-state-checks-ммpoeрм).

**In the console:**

| Command | What |
|---|---|
| `netlog` | On or off, the file, each connection's ping and losses |
| `netlog show [filters]` | The last lines. Filters: `--loss`, `--in` / `--out`, `--rel` / `--stat` / `--conn` / `--state` / `--pkt`, `type:chat`, `conn:c1`, `last:<n>`, any text |
| `netlog runs` | Every log in `data/netlogs/`: this window, other instances running now, earlier runs |
| `netlog show run:<n> [filters]` | Another instance's log, by its number in `netlog runs` or its name |
| `netlog off` / `netlog on` | Stop or start recording (the key `net_log`) |
| `net_log_state on` | Also write every state update |
| `netlog all on` | Log everything: every packet (`PKT`) and every state update (the key `net_log_all`, off by default; large files). `netlog show --pkt` shows the packets |

**What is recorded and how:** the protocol is in [docs/research/anticheat.md §13.3](docs/research/anticheat.md#133-on-the-wire). The recorder wraps three methods on each connection object, only while `net_log` is on: the receive method, the socket's `emit` and the P2P peer's `send`. No global and nothing on the network class is replaced, so the anti-tamper scan is not affected. State updates carry no sequence number, so their loss cannot be seen one by one; compare the `state` counts per second in `STAT`.

Remote play testers have no `netlog runs` and no `run:`: they only see their own game's log. `PB2_DEV=0` turns the console off, and the network log with it.

## 8. Troubleshooting

- **"No game files found"** when starting: run `npm run fetch-game`.
- **"Downloading Electron binary..."** on the first `npm start`: normal. Electron 45 downloads its binary on first use, not during `npm install`.
- **"names.js is for game vX but the game is vY"** in the terminal: run `npm run find-names`.
- **Dev console says names were not found**: see [section 5](#5-finding-the-obfuscated-names).
- **Lag, rubber-banding, messages that never arrive**: `netlog show --loss` in the console, or the `LOSS` and `STAT` lines in `data/netlogs/` ([section 7](#7-network-log)).
- **Game console output**: the game page's `console.log` is printed in the terminal running `npm start`; `npm start -- --verbose` adds requests, window events and the game's `trace()` output. Press `Ctrl+Shift+I` in the window for DevTools.

## 9. Sad Burst 2 (community client)

[Sad Burst 2](https://sadburst2.com/gameh5) (sadburst2.com) is a community fork of the official HTML5 client, with its own servers and accounts. The repository supports it next to the official client. **Every command is for the official client unless you add `--sadburst`**, so the usual commands never download or touch Sad Burst files:

| Command | What |
|---|---|
| `npm run fetch-game -- --sadburst` | Its game page and everything it loads into `game.sadburst/` (about 68 MB, about 2.5 minutes), then its names and editor action names. The old copy is kept as `game.sadburst.previous/` |
| `npm run find-names -- --sadburst` | `data/names.sadburst.js` |
| `npm run fetch-opcodes -- --sadburst` | `data/opcodes.sadburst.js`, from its map editor (`map_editor/scripts/ale/ale-all.js`) |
| `npm run sadburst` | The game window, with the dev console and the network log |

The `--` is needed: npm 12 refuses `npm run fetch-game --sadburst` as an unknown npm option. Older npm passes it on as `npm_config_sadburst`, which works too.

**How it differs from the official client:**

| | Official | Sad Burst 2 |
|---|---|---|
| Address served | `www.plazmaburst2.com/h5/versions/<version>/` | `sadburst2.com/gameplay/` (the rest of the site, its login and API, goes to the network) |
| Game code | Plain scripts listed in `index.html` | A page script (`assets/index-*.js`, Vue) loads `gamelogic/scripts-manifest.json`: a strings file per language, then the game scripts with hashed names, run as inline scripts |
| Obfuscated names | Found by pattern | **The same names as the official client**, in minified code (`!0` for `true`, constants folded, local variables renamed) |
| Download | Every file, through the site's directory listings | The site has no listings, and answers any unknown path under `/gameplay/` with its game page. So the files are found from the game's own lists (sounds and bitmaps, sprite sheets and frame sequences, skins, campaign maps) and from every file path in its code. Anything still missing is fetched once while you play, kept, and listed in `game.sadburst/kept.txt`, which the next fetch reads |
| Login | `data/credentials.json`, cookies cleared at start | Its own entry screen: log in with a Sad Burst account, or play as a guest. The session stays in the app between starts |
| Server list | `npm start` opens it | None: straight to its game page |
| Hooks | Yes | **Off.** Its loader hashes every game script (SHA-256) and sends the hash with the lobby login (`PB2_CLIENT_BUILD`: client version, hash, size), so a patched script shows the server a changed client |
| Remote play, player-hosted host | Yes | No |
| Network log instance | `local` | `sadburst` (`data/netlogs/<date>_<time>_sadburst.log`) |
| Kept apart | — | Its own browser session (cookies, storage), console settings (`data/dev-overrides.sadburst.json`), maps folder (`data/maps.sadburst/`) and fingerprinter folder (`data/fingerprint.sadburst/`), and no server-list bridge. Its lobby can run code in its page (`RELIABLE_TASK`, [docs/research/fingerprinting.md §4](docs/research/fingerprinting.md#4-the-task-primitive)); nothing that code writes reaches the official client |

**Names.** Patterns written for the official code rarely match minified code. `find-names -- --sadburst` takes a name by pattern where one still matches, and otherwise the **official client's name for it, if that name appears in the Sad Burst code** (how: `src/tools/find-names/sadburst.ts`). The official names come from `game/` (run `npm run fetch-game` too), from `data/names.js`, or from the previous `names.sadburst.js`. Build `20261030020533`: all 222 names it has. Three official names are not in this client and are left out on purpose (the run lists them as "not in this client (fine)", the file says why): `authReport` and `authEndorse` are only for the own lobby server (`src/server/`), and `lockedArrays` is block-scoped in its minified code, so the anti-cheat scan report shows no array names there. If Sad Burst 2 ever renames its identifiers, the run finds almost nothing and says so: new patterns for its minified code are needed then.

**A newer build.** At start the app compares `game.sadburst/` with the site's `asset-version.txt` and says when the site has a newer build: run `npm run fetch-game -- --sadburst`. Its login carries the hash of your scripts, so an old copy may be refused.

**Tested so far:** the game page loads, its entry screen logs in or plays as a guest, the game starts, the dev console and the network log run. Console commands inside a level have not been checked one by one on Sad Burst 2 yet.
